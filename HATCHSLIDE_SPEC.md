## 2. Core mechanic and exact rules

A swipe slides every mobile piece one cell per tick, all at the same time, until each piece is blocked; the level is won when every hatchling reaches the ocean before the seagull counter hits zero.

**Board:** a grid from 5x7 up to 9x12 cells. Cell (0,0) is top-left. Screen-up always equals board-up; the camera never rotates the board, so swipe directions stay intuitive.

**Mobile pieces:** hatchlings and coconuts. Everything else is a fixed tile or a scripted hazard.

**Move resolution (deterministic, tick-based):** implement this exactly in `core/game`, with no Android dependencies.

1. The player swipes UP, DOWN, LEFT or RIGHT. Every mobile piece gets that direction and is marked *moving*.
2. Each tick, every moving piece computes its target cell = position + direction.
3. A piece **stops** if the target is outside the board, a blocker tile, or occupied by a piece that is not moving.
4. If two pieces target the same cell, the piece that is frontmost along the swipe direction wins (ties broken by piece id); the other stops.
5. A piece may enter a cell that another piece is leaving in the same tick (pieces follow each other in a line). Resolve chains with a fixed-point pass until no decision changes.
6. After entering a cell, apply that tile's effect (section 3): stop, redirect, teleport, fall, break, or reach the ocean.
7. A hatchling that enters an ocean cell is **saved** and removed at the end of that tick, which frees the cell for pieces behind it.
8. Repeat ticks until no piece is moving. Safety: if a piece repeats the same (cell, direction) within one move, stop it; cap ticks at width x height x 4.
9. After sliding ends, advance scripted hazards one step (crabs, gull shadows, egg timers), then evaluate win and lose.

**The simulator returns a `MoveResult`:** per-piece list of cells visited per tick, plus typed events (`Stopped`, `Saved`, `Redirected`, `Teleported`, `FellInPit`, `ShellCracked`, `Hatched`, `CrabStepped`). The renderer animates from this result; it never changes game state itself.

**No-op moves:** if no piece moves, the move does not count, the counter does not drop, and the game plays a soft bump animation, sound and `REJECT` haptic.

**Seagull counter:** each level has `gullMoves`. The HUD shows a seagull icon with the moves left. At 3 moves left the gull's shadow starts circling the board; at 1 move left the HUD ring pulses and the gull calls.

- **Win:** all hatchlings saved on or before the last allowed move.
- **Lose:** the counter reaches zero with any hatchling still on the sand, or a hatchling falls into a sand pit, or a hatchling ends a move under a gull shadow (world 5).
- **Lose animation (keep it gentle for an all-ages rating):** the gull swoops low, the hatchlings duck into their shells, the gull lands on a rock and squawks. No grabbing, no injury.

**Stars:**

| Stars | Condition |
| --- | --- |
| 3 | Moves used <= par (the solver's optimal move count) |
| 2 | Moves used <= par + 2 |
| 1 | Level completed before the gull swoops |

**Undo, restart, hint:**

- Undo is unlimited and restores the full state, including the gull counter and hazard timers.
- After a loss, offer both **Undo last move** and **Retry**.
- Hint runs the solver from the current state and shows a ghost arrow for the next optimal move. If the current state cannot be solved in the moves left, the hint says so and highlights Undo.
- Hints are free and unlimited, and never block stars.

**Input feel:** register the swipe on `ACTION_MOVE` once it passes 24 dp with an angle within 35 degrees of an axis, not on finger lift. Buffer at most one swipe during an animation and run it when the current move ends. Ignore swipes that start inside system gesture insets so the game never fights the back gesture. Also accept keyboard arrows/WASD and gamepad D-pad.

## 3. Tiles, obstacles and hazards

The game has 14 cell types introduced across 5 worlds; each new type gets two easy showcase levels and a one-card tip the first time it appears.

| Cell | Level char | Rule | First world |
| --- | --- | --- | --- |
| Sand | `.` | Pieces slide over it | 1 |
| Hatchling start | `T` | A hatchling starts here on sand; hatches from an egg in the intro animation | 1 |
| Rock | `#` | Blocker | 1 |
| Shell | `S` | Blocker (3 visual variants: scallop, conch, cowrie) | 1 |
| Ocean | `~` | Goal. A hatchling entering it is saved. Coconuts entering it sink and are gone | 1 |
| Wet sand | `w` | A piece that enters it stops on it | 2 |
| Cracked shell | `C` | Blocker the first time a piece hits it, then breaks into sand | 2 |
| Current arrows | `>` `<` `^` `v` | A piece entering it changes direction to the arrow's direction and keeps sliding | 3 |
| Coconut | `o` | Mobile piece. Slides like a hatchling, is never saved, fills sand pits | 3 |
| Sand pit | `O` | A hatchling entering it falls in (lose). A coconut entering it fills it; it becomes sand | 3 |
| Crab | `c` + patrol path | Moving blocker. Steps one cell along its ping-pong path after each move; waits if its next cell is occupied | 4 |
| Late egg | `e` + timer | Blocker that hatches into a hatchling after N moves; that hatchling must also be saved | 4 |
| Tide pool pair | `1`-`4` (pairs) | A piece entering one pool exits from its twin and keeps sliding the same direction. If the twin is occupied, the entry pool acts as a blocker | 5 |
| Gull shadow | path in JSON | Shadow covers 1 cell and moves along a loop after each move. A hatchling that ends a move under it loses the level | 5 |

Rules every cell type follows:

- Hatchlings are identical for solving purposes and block each other.
- Fixed decorations (palms, umbrellas, driftwood, lanterns) sit outside the grid and never affect play.
- Every tile must read clearly by **shape and silhouette**, not colour alone, so the game works in colour-blind mode.
- Each tile type has a unit-test fixture covering entry from all four directions.

**Solver (`core/game`, shared by the app and the tools):**

- Breadth-first search over states; depth limit = `gullMoves`.
- State = sorted hatchling cells (they are identical) + coconut cells + broken shells + filled pits + crab phases + egg timers + gull shadow phase. Pack it into a `LongArray` key and store visited states in a hash set.
- Returns optimal move count, one optimal path, and the number of optimal first moves (used for difficulty scoring).
- Must solve any shipped level in under 200 ms on a mid-range phone, because the in-game hint uses it.

**Generator (`tools/levelgen`, a JVM command-line program):**

1. For each world, place random tiles from that world's rule set using a seeded RNG.
2. Run the solver. Reject the board if it is unsolvable, its par is outside the world's range, a single repeated direction solves it, or the optimal path never uses the world's new mechanic.
3. Score difficulty from par, branching factor, number of optimal solutions (fewer is harder) and dead-end count. Sort accepted boards into a smooth curve with a small breather level every 5th level.
4. Write the JSON files and commit them, so builds are reproducible.

**Hand-made tutorial:** levels 1 to 10 of world 1 are written by hand. Level 1 is a 1-hatchling, 1-swipe board; level 2 shows two hatchlings sliding together; level 3 shows one hatchling blocking another; level 4 introduces rocks as stoppers; by level 10 the player has used all four directions.

**Daily Tide:** 366 pre-generated puzzles bundled in `assets/levels/daily.json`, picked by the device's local day of year. Track the streak locally. No network and no runtime generation.

**Unlocks:** world N+1 opens when world N is completed; each world's last 5 levels need 45 total stars in that world to open, so players replay for 3 stars without hitting a hard wall.

## 6. 3D art direction and rendering

The look is a premium stylized diorama: a hand-crafted toy beach at golden hour, soft and warm, with stylized PBR rather than photorealism.

**Engine:** Filament with `gltfio` for models, `filament-utils` for IBL/KTX loading, OpenGL ES 3.0 backend. Host it in a `SurfaceView` through Filament's `UiHelper`, drive frames with `Choreographer`, pause rendering in `onPause`, and destroy every Filament object in reverse creation order. Write custom materials (water, foam, sand, shadow decal) as `.mat` files in `materials/` and compile them with `matc` from the exact same Filament release as the runtime library.

**Camera:**

- Perspective, 35 degree FOV, about 55 degree pitch, no yaw, so screen-up is board-up.
- Idle sway of plus or minus 0.6 degrees; small shake (2 frames) when a piece stops hard.
- Level start: 1.2 s dolly from a wide shot over the ocean down to the board.
- Win: follow the last saved hatchling into the surf, then tilt toward the horizon.
- Auto-frame the board to the free viewport between HUD bars on every resize.

**Board and island:** each cell is a softly bevelled tile with tiny height noise; the grid sits on an island chunk with sculpted cliff sides, so it reads as a diorama. Sliding hatchlings leave footprint decals that fade over 4 s.

**Water (the showpiece):**

- A large ocean plane around the island with 4 summed Gerstner waves in the vertex shader.
- Two scrolling normal maps, Fresnel reflection of the sky, sun glints, shallow turquoise to deep blue colour by distance from shore.
- A shoreline distance texture baked per level from the tile map drives an animated foam band that laps in and out.
- World 3 night: emissive bioluminescent foam that flares where hatchlings enter the water.

**Lighting and sky:** one directional sun with soft shadows (VSM or PCSS on High), plus IBL. Each world has its own HDR sky and grade: peach sunrise, bright noon, moonlit night with stars, warm late afternoon, orange volcanic dusk with haze.

**Hatchling (the hero):** about 0.8 of a cell, big expressive eyes, shell with clear scute pattern, 7 species skins. Procedural animation in code:

- Head turns toward the swipe direction 60 ms before moving (anticipation).
- Flippers paddle at about 2.5 Hz while sliding; body leans into the motion.
- Squash to 85% height on stop, spring back.
- Random blink every 2 to 5 s and a small idle wiggle.
- Save: dive into the wave, splash, sparkle, then swim away visibly.
- Level start: eggs crack and hatchlings pop out 80 ms apart.

**Other models:** 6 rock variants, 3 shell types plus cracked shell, coconut, crab with animated claws, sand pit with sand rim, current channel with flowing stripes, glowing tide pools, a late egg that wobbles one move before hatching, seagull with flap and glide cycles, palms, driftwood, beach umbrellas, lanterns, coral, starfish. Every model has LOD0 and LOD1.

**Particles:** sand trail while sliding, sand puff on stop, splash and spray on save, shell confetti on 3 stars, firefly-like sparkles at night, ash drift in world 5. Use instanced quads with a pooled particle system; never allocate per frame.

**Post-processing (Filament `View` options):** ACES-style tone mapping with per-world colour grading, subtle bloom, SSAO, TAA or FXAA, light vignette, distance fog at the horizon, dynamic resolution.

## 8. Asset pipeline and size budget

Target about 145 MB download for an arm64 phone, built entirely from assets the game renders or plays, and delivered as a base module plus one install-time asset pack.

**One command builds everything:** `python tools/assetgen/build_all.py` (also wired to a Gradle task `generateAssets`). It is deterministic (fixed seeds), skips unchanged outputs, and writes a manifest `assets_manifest.json` listing every output file, its size and which code references it.

**3D models** (`tools/assetgen/models/`):

- If Blender is on PATH, build models with `blender -b -P` scripts: bevel, subdivision, displacement noise, baked AO into vertex colour or ORM textures, export `.glb`.
- Otherwise build them in Python with `trimesh` + `numpy` + `pygltflib`: parametric meshes, smooth normals, proper UVs, vertex colours.
- Every model: real-world scale (1 unit = 1 cell), PBR materials, LOD0 and LOD1, under 15k triangles for LOD0 of a hero model.

**Textures** (`tools/assetgen/textures/`): tileable fBm, simplex and Worley noise for golden, coral-white, black volcanic and wet sand; rock; shell nacre; 7 turtle scute patterns; water normals; foam; caustics; clouds. Output albedo, normal and ORM sets at 2048 (hero surfaces 4096), then compress with Filament `mipgen` to mipmapped KTX in two formats: ASTC and ETC2.

**Skies and IBL:** render one HDR equirectangular sky per environment (title + 5 worlds) at 4096x2048 with a physically inspired gradient, sun or moon disc, procedural clouds and stars; convert with Filament `cmgen` into IBL (specular + spherical harmonics) and skybox KTX files.

**UI art:** vector drawables and Compose Canvas for buttons and icons so they stay sharp at any density; adaptive launcher icon with foreground (hatchling face), background (waves) and monochrome layer for themed icons.

**Fonts:** download the chosen OFL fonts from the Google Fonts GitHub repository at build time, bundle them in `res/font`, include `OFL.txt`.

| Textures (one compression format per device) | 5 world sets, 7 turtle skins, water, foam, FX | 70 MB |
| Skies and IBL | 6 environments | 18 MB |
| Music | 6 tracks + 2 stingers | 30 MB |
| Effects and ambience | \~40 SFX + 4 loops | 8 MB |

| Code + Filament native libs (one ABI per device) | Kotlin, Compose, Filament | 9 MB |

**Delivery:**

- Put textures, skies and music in an install-time asset pack `hd_assets`; it downloads with the app, so the game stays offline after install and needs no permission.
- Use texture compression format targeting: folders `textures#tcf_astc` and `textures#tcf_etc2`, so each device downloads only one format.
- Google Play's limits are 200 MB for the base module, 1.5 GB per asset pack and 4 GB cumulative for install-time content; above 200 MB, mobile-data users see a size warning, which is why the target stays near 145 MB ([Play size limits](https://support.google.com/googleplay/android-developer/answer/9302563)).

**Size rules:** no padding files, no unused assets (a test checks every manifest entry is referenced), no uncompressed duplicates. Measure the real per-device download with `bundletool` and write it to `SIZE_REPORT.md`; the build gate fails outside 100 to 190 MB.

```text
├─ hd_assets/            Install-time asset pack (textures, skies, music)
├─ baselineprofile/      Macrobenchmark + baseline profile generator
├─ materials/            Filament .mat sources
├─ tools/levelgen/       JVM CLI: generator + solver → level JSON
├─ tools/assetgen/       Python: models, textures, skies, audio, build_all.py
├─ assets_src/           Intermediate sources and optional CC0 overrides
├─ store/                Listing text, screenshots, feature graphic, privacy policy
└─ README.md, DECISIONS.md, LICENSES.md, SIZE_REPORT.md
```

**Runtime architecture:**

- Unidirectional data flow: `GameViewModel` holds an immutable `GameState` in a `StateFlow`; a swipe calls `Simulator.apply(state, direction)`, which returns the new state plus a `MoveResult`.
- The renderer receives the `MoveResult` and animates it; input is locked only for the buffered-swipe rule in section 2.
- Compose draws the HUD above a Filament `SurfaceView` hosted with `AndroidView`.
- Declare `android:configChanges` for orientation, screen size, smallest screen size, screen layout, density and UI mode on the Activity, and resize the Filament viewport instead of recreating the surface. Save the in-level state (`GameState` + undo stack) in `SavedStateHandle` and DataStore so process death resumes the same board.
- Load each world's assets on a background dispatcher, upload to Filament on the render thread, and release the previous world's textures on world change.
- Enable Android auto-backup and device transfer of the DataStore files through `dataExtractionRules`, so progress survives a reinstall with no permission.

## 10. Android 17 and Google Play compliance (fast-approval checklist)

Approval speed comes from a clean policy profile, not from app size: target API 37, zero permissions, no data collected, aligned native libraries, an honest listing, and a completed closed test.

**Platform and build:**

- Target API 37. Play has required API 36 or higher for new apps and updates since August 31, 2026, so 37 is ahead of the rule ([Play target API requirements](https://developer.android.com/google/play/requirements/target-sdk)).
- Set `android:appCategory="game"` on the application. Apps targeting API 37 can no longer lock orientation or resizability on screens 600 dp and wider, and games are the stated exception ([Android 17 orientation change](https://developer.android.com/about/versions/17/changes/ff-restrictions-ignored)). Still support every orientation and window size properly, as section 5 requires.
- 16 KB page sizes: Filament ships native `.so` files, so verify every arm64-v8a and x86\_64 library is 16 KB aligned with `zipalign -c -P 16` and `llvm-readelf`, and that it passes the APK Analyzer check ([16 KB guide](https://developer.android.com/guide/practices/page-sizes)).
- ABIs: arm64-v8a, armeabi-v7a, x86\_64. Drop x86.
- Release AAB signed with an upload key read from `keystore.properties` or environment variables (never committed), Play App Signing, R8 full mode, `shrinkResources`, `debuggable false`.
- Edge-to-edge with correct insets and display cutouts; immersive mode during gameplay; predictive back as in section 5.
- Game Mode: add `res/xml/game_mode_config.xml` (battery and performance modes) and read `GameManager.getGameMode()` on API 31+ to pick the default tier.

**Zero-permission gate (scripted, runs in `./gradlew check`):**

- Parse the merged release manifest and fail if any `<uses-permission>` exists.
- Defensively add `tools:node="remove"` entries for `INTERNET`, `ACCESS_NETWORK_STATE`, `WAKE_LOCK`, `VIBRATE`, `POST_NOTIFICATIONS`, `FOREGROUND_SERVICE`, `RECEIVE_BOOT_COMPLETED` and `com.google.android.gms.permission.AD_ID`.
- AndroidX Core adds an app-internal `DYNAMIC_RECEIVER_NOT_EXPORTED_PERMISSION`. Do not register dynamic broadcast receivers, then remove both its `<permission>` and `<uses-permission>` entries. If a dependency truly needs it, keep it and document in `DECISIONS.md` that it is a signature permission with no user prompt.
- Keep the screen awake during play with `FLAG_KEEP_SCREEN_ON`, which needs no permission.
- Grep gate: no `java.net`, `okhttp`, `HttpURLConnection` or `WebView` usage anywhere.

**Play Console answers (write them into `store/console_answers.md`):**

- **Data safety:** no data collected, no data shared. Google still requires every app to complete this form and link a privacy policy, even with no data collected ([Data safety help](https://support.google.com/googleplay/android-developer/answer/10787469)).
- **Privacy policy:** write `store/privacy_policy.md` and a one-page `privacy_policy.html` the developer can host free (for example on GitHub Pages); show the same text offline in Settings.
- **Ads:** No. **In-app purchases:** No. **App access:** all content available without login.
- **Content rating (IARC):** no violence, no fear themes, no user interaction, no gambling. Expect Everyone / PEGI 3.
- **Target audience:** decide before upload. Choosing 13+ keeps review simplest; including under-13s brings the Families policy, which this game already meets because it has no ads, no data collection and no third-party SDKs.
- **Category:** Game › Puzzle.

**New personal developer accounts:** an account created after November 13, 2023 must run a closed test with at least 12 testers opted in for the last 14 continuous days before applying for production ([testing requirements](https://support.google.com/googleplay/android-developer/answer/14151465)). Plan for it: internal test first, then closed test, ship one small update during the 14 days, and keep `store/test_notes.md` with what testers reported and what you fixed; the production-access form asks for exactly this.

**Pre-launch report readiness:** no login walls, all controls have content descriptions so the Play test robot can navigate, no crash or ANR in a 10,000-event `adb shell monkey` run.

**Listing honesty:** screenshots must be real gameplay; no other games' names or trademarks in title, description or tags; no claims like "#1" or "best".

## 11. Performance and device adaptation

Hit 60 fps on a mid-range phone, never drop below 30 fps on a 3 GB RAM phone, and reach the interactive title screen in under 1.5 s from a cold start.

| Metric | Target | How it is measured |
| --- | --- | --- |
| Gameplay frame rate, mid-range (Medium tier) | 60 fps, under 2% janky frames | Macrobenchmark `FrameTimingMetric` |
| Gameplay frame rate, low-end (Low tier) | 30 fps stable | Macrobenchmark on a low-RAM emulator profile |
| Cold start to interactive title | Under 1.5 s mid-range | Macrobenchmark `StartupTimingMetric` with baseline profile |
| Swipe to first visible movement | Under 50 ms | Timestamp log in debug builds |
| Peak memory (High tier) | Under 450 MB PSS | `dumpsys meminfo` during world 5 |
| World switch load | Under 800 ms, with an animated tip screen if over 300 ms | Debug timing log |

**Techniques:**

- Baseline profile generated by the `baselineprofile` module, covering startup, menus and one full level.
- Zero allocations per frame in the render loop: preallocated matrices, pooled particles, reused event lists.
- Android Dynamic Performance Framework: a `PerformanceHintManager` session for the render thread and `PowerManager.getThermalHeadroom()` to step the quality tier down before the device throttles (API 31+; no permission).
- Menus render on demand: when nothing animates, drop to 30 fps; stop rendering entirely when the app is backgrounded.
- Frame rate setting from section 5, applied with `Surface.setFrameRate`.
- Instanced drawing for repeated props, texture atlases for small decor, LOD1 at distance.

**Adaptation:** support phones, tablets, foldables (fold and unfold mid-level without losing state), desktop windowing and Chromebooks; keyboard, mouse and gamepad input; window size classes for HUD placement; no letterboxing.

## 12. Testing and verification gates

Every gate below runs from `./gradlew check` or a script in `tools/verify/`, and a milestone is done only when its gates are green.

**Game logic (`core/game` unit tests):**

- One fixture per tile type, entering from all 4 directions.
- Simultaneous sliding: lines of hatchlings follow each other; same-cell conflicts resolve by the frontmost rule; saved hatchlings free their cell for followers.
- Current loops stop safely; coconut fills pit; crab waits when blocked; egg hatches on the right move; tide-pool exit blocked case.
- Undo restores identical state (compare hashes); a no-op move changes nothing.
- Property test: 10,000 random move sequences on random boards never crash and never change the piece count except by saves, pits and hatches.

**Level validation:** every one of the 150 levels and 366 dailies loads, is solvable within `gullMoves`, has stored `par` equal to the solver's optimum, and every mechanic-intro level uses its mechanic in the optimal path.

**UI and lifecycle (instrumented):**

- Navigation through all 14 screens; settings persist across restart.
- Rotate, fold and resize mid-animation: board state and undo stack survive.
- Process death in the middle of a level resumes the same board.
- Background and foreground: audio pauses and resumes, rendering stops and restarts.
- Rendering smoke test on an emulator: title and one level render without GL errors; save screenshots.

**Release gates (scripts):**

- Merged manifest: `targetSdk 37`, `appCategory game`, zero `<uses-permission>`.
- No network code (grep gate from section 10).
- 16 KB alignment check on every native library.
- `SIZE_REPORT.md` shows per-device download between 100 and 190 MB.
- Every file in `assets_manifest.json` is referenced by code; nothing unreferenced ships.
- Lint with zero errors; ktlint or detekt clean; no `TODO` in `src/main`.
- 10,000-event monkey run with zero crashes and ANRs.
- Macrobenchmark results meet section 11 on the emulator reference profile; record numbers in `DECISIONS.md`.

**Devices to test on (emulators are fine):** phone API 26, 30, 35 and 37; a 16 KB page-size system image; tablet; foldable; resizable desktop window.

## 14. Build order and definition of done

Build in 10 milestones, each ending with its gate green and a short entry in `DECISIONS.md`; the game is done when every box below is ticked.
